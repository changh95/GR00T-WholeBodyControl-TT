## S2 bring-up (hold A, stage-0 boot)

Host NoC writes cannot initialise LIM: the CCACHE pre-reads uninitialised SRAM, poisons the ECC, and the poison
survives `tt-smi -r`. E1F (the user's DP3(d) approval) boots a 64 B stage 0 from the GP scratch that zero-fills LIM
from the hart, then the host loads the monitor. After that: SELFTEST over all 30,720 lines, BEU 0, 0 traps; RNMI re-arm
10/10; mcycle/mtime 16; PLL4 relock across legacy fd churn with no heartbeat gap (E3); re-attach without a release
(E3(d)). E2m: one hart streams LIM at ~7.9 B/cycle (6.3 GB/s) with 64-512 B vector loads; a dependent load is ~28 cycles.

## Kernels (E4 / E5a, session s3v3)

| Variant | dtype | compute p99 | vs ORT, max \|Δa\| | vs x86 build |
|---|---|---|---|---|
| v0 (scalar) | fp32 | 5.27 ms | 2.6e-6 | bit-identical |
| v1 (vector) | fp32 | 0.332 ms | 2.6e-6 | bit-identical |
| v2 (vector) | fp16 | 0.385 ms | 8.5e-4 | bit-identical |
| v2s (strided) | fp16 | 9.37 ms | 8.5e-4 | bit-identical |
| **v3** (one vector op less per weight group) | fp16 | **0.278 ms** | 8.5e-4 | bit-identical |

v3 is 222,416 cycles per call against v2's 307,974 (0.72x) and is the default. One hart's vector ALU pipe is the
limit (39 cycles per weight row), not the LIM port.

Host path: the per-INFER overhead went from ~301 µs to ~140-240 µs after two fixes: the monitor's bitwise CRC became
slicing-by-8 (124K → 13.6K instructions per INFER), and kmd's op log, whose list halved itself every 65,536 ops (a 2-7 ms
stall every ~1,070 calls), became a bounded deque. x280d `serve --spin` busy-polls with a `sched_yield` per miss.

## S3b: 4 harts on one tile

Harts 1-3 of L2CPU3 are adopted by RNMI after release (wake 7-10 mtime ticks, BEU 0). One hart with vector loads already
reaches the tile's LIM read ceiling (~6.4 GB/s). The MLP proxy scales 2.62 → 5.05 → 5.10 GB/s for 1 → 2 → 4 harts
(S_4 = 1.94), and background LIM streaming slows hart 0's INFER by 75%, so the MLP is not split across harts of one tile.
More bandwidth needs more tiles (L2CPU0-2, each with its own LIM): the next step (below).

## T-3.8 fault injection (`jobs/m3_faults.sh`)

The first run (S4) lost the tile on case 2: after kill -9 and re-attach, the RNMI PARK never came back, and every L1/L36
field read 0. Root cause: the RNMI ran stage 0 again from a stale line in hart 0's L1I. Stage 0 ends `fence.i; jr a0`,
which refetches its own 64 B line at 0x2001_0100, and nothing on hart 0 ran `fence.i` after the host swapped the park
stub into the GP scratch; the image's .text fit in one 16 KiB way of the 2-way L1I, so the line was never evicted. The
kill and attach were not involved (S2's PARKs passed only because a code LOAD had sent FENCE_I first). Fix (commit
e87e7f7): crt0 runs `fence.i` on every entry of hart 0, and E1F step E sends FENCE_I right after the swap; either alone
fixes it on the sim, which now models hart 0's L1I line.

Rerun t38c (fixed image, build_id 306483273):
- PARK as the first command after READY (the case that re-ran stage 0 every time on the old image): pass, warm entry,
  n_reentry 0 → 1, state REENTERED, then SELFTEST and a 500-row parity run pass.
- The three cases during a 150 s RT run (seeds 2100-):

## T-3.9 soak (`jobs/m3_soak.sh`, X280 only)

The user decided that the GPU WBC has no place in M3, so T-3.9 runs X280-only (no WBC swaps; fault demos use the
host-CPU ORT only), with the HUD and the recording on.

t39b (cut at 57 min by a machine reboot): 108 episodes, 19 successes, 0 starved ticks, 0 VLA errors; x280d 144,871
calls, all OK (0 timeouts, faults, stalls); 6 loop fallbacks at the 8 ms timeout (plus one at the reboot). In each, the
request reached x280d 8-19 ms after rt_sim sent it, and x280d then answered in its usual ~0.55 ms, so the delay is
before x280d's receive, not on the chip. The GPU WBC on the same loop had 1 fallback at 5 ms in 2 h (T-2.8). t39c
sampled every x280d and rt_sim thread's run-queue wait to find which side waits.

t39c (`rtloop-m3e` snapshot at e87e7f7, `--wbc-timeout-ms 8`, HUD and recording on, no other load on the host): the
user stopped it at 107 min (SIGINT), so the summary's only failing row is `loop_rc` 130.

t39b's six fallbacks came from load on the host, not from the chip or x280d: t39b ran next to a debugging agent's
test runs on CPUs 0,1,16,17,24-27, t39c ran with background work limited to CPUs 0-1 and had no fallbacks. A run-queue
sampler (every x280d and rt_sim thread, 1 ms) puts the remaining slow ticks on the zmq I/O threads: rt_sim's (CPU 3,
shared with its helper thread) and x280d's (CPU 5, shared with its busy-polling main thread) wait about 3 ms for their
CPU, one EEVDF base slice. Moving each I/O thread to its own CPU (for example x280d's to CPU 21) would remove that
tail; not needed at the 8 ms timeout.

Soak length: the user judged 2 h more than a demo needs. Later soaks default to ~30 min (T-2.6 shape); 2 h only before a
demo that will run for hours.

## Success rate and "bad actions"

The closed-loop success rate is the checkpoint's, not the chip's. Same seeds 3000-3107: Tensix VLA + X280 WBC 19/108
(t39b), Tensix VLA + GPU WBC 24 (T-2.8), GPU + GPU 22 (T-1.10); McNemar p ≈ 0.38 between the first two. The X280 matches
the ORT reference to 8.3e-4 on every tick, and the chunk-boundary jump (p99 0.18-0.19 rad) and the chunk age are the
same in all three. The cloudwalk fine-tune succeeds 20-30% of the time in this env on any backend.
